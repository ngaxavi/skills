# When a controller manages the object: GitOps, operator-synced Secrets, and drift

Much of what breaks in a modern cluster is not the workload itself but the
*machinery that manages it*: a GitOps controller reconciling toward Git, an operator
syncing or generating Secrets, a Helm chart whose generated values have drifted from
an already-initialized datastore. The common thread is a gap between **declared
desired state** and **live state** — and a live `kubectl` change is the wrong tool
when something is actively reconciling the object back.

None of this is vendor-specific. Argo CD, Flux, External Secrets Operator, Sealed
Secrets, Vault, and cloud secret managers are named below only as the common
examples of general patterns.

<a id="gitops"></a>
## GitOps: Synced vs Healthy, and drift

A GitOps controller (Argo CD, Flux) continuously reconciles cluster state toward a
Git repository. Two independent statuses matter, and conflating them misleads:

- **Synced / InSync** — live state matches the Git manifest. Says nothing about
  whether the app actually works.
- **Healthy** — the workload's own health checks pass. Says nothing about whether it
  matches Git.

The four combinations each mean something different:

| Synced | Healthy | Meaning |
|---|---|---|
| yes | yes | nominal |
| yes | no | Git is deployed but the app is broken — debug the workload (core skill) |
| no | yes | live drift: something was patched by hand, or Git moved and sync is lagging |
| no | no | often a bad manifest just rolled out, or reconciliation is stuck/paused |

```bash
kubectl get applications -A                          # Argo CD: SYNC + HEALTH at a glance
kubectl get kustomizations,helmreleases -A           # Flux equivalents
kubectl describe application <app> -n <argo-ns>      # conditions, last sync, revision, message
```

Things to check when GitOps is in the picture:

- **Live revision vs Git revision.** If the app's deployed revision lags the repo
  HEAD, sync is stuck or paused — look for a failed hook, a disabled auto-sync, or a
  reconciliation error in the controller's events, not a workload bug.
- **App-of-apps staleness.** A parent Application that itself is `OutOfSync` will not
  roll changes to its children; the child looks "unchanged" for reasons that live
  one level up. Walk up the ownership chain.
- **Source-of-truth vs live patch.** This is the operational rule: if a controller
  reconciles the object, a `kubectl edit`/`patch` is reverted on the next sync
  (often minutes). Fix the **Git manifest**, let it reconcile, and verify the live
  revision advanced. A live patch is a deliberate, temporary stopgap — never the
  final fix — and if you must, know it will be undone.

<a id="secrets"></a>
## Secrets synced or generated by an operator

When a `Secret` is "missing," first decide whether something is *supposed to create
it* — an operator that syncs from an external store or generates it. A missing
Secret and a failed sync look identical from the consuming pod (stuck
`ContainerCreating`, `MountVolume ... secret "x" not found`) but have opposite
fixes.

```bash
kubectl get externalsecrets,secretstores,clustersecretstores -A   # External Secrets Operator
kubectl describe externalsecret <name> -n <ns>                    # SecretSynced condition + reason
kubectl get sealedsecrets -A                                      # Sealed Secrets, etc.
```

- **Missing vs sync-failure** — if an `ExternalSecret` (or equivalent) exists but its
  status is not `SecretSynced`, the Secret was never written because the *sync*
  failed; the target Secret's absence is a symptom. Read the condition reason.
- **Key mismatch** — the Secret syncs, but the `key`/`property` the operator pulls
  does not match what the app expects (`FOO` vs `foo`, a renamed field in the
  provider). The Secret exists and is wrong, which is harder to spot than absent.
- **Provider timeout / flapping** — the backing store (Vault, a cloud secret
  manager) is slow or intermittently unreachable, so the Secret appears and
  disappears or goes stale. Check the `SecretStore` validation status and the
  operator's logs for auth/network errors to the provider.
- **Hygiene** — do not `kubectl get secret -o yaml` and paste values into logs,
  tickets, or an agent transcript; the data is base64, not encrypted. Report *that*
  a key is missing or mismatched, not its value.

<a id="drift"></a>
## Credential drift: regenerated Secret vs initialized datastore

A specific, common, and confusing failure: a Helm chart (or operator) **generates a
random password into a Secret at install time**, but the stateful app initialized
its persistent volume with the *first* password and never re-reads it. Later, the
Secret is regenerated — a `helm upgrade` without pinning the value, a re-render, a
recreated Secret — and now the Secret holds a new password while the datastore on
disk still expects the old one. The app authenticates against itself and fails.

The signature: a database/message broker/identity server that was fine suddenly logs
`password authentication failed` or `access denied`, with **no change to the app
image or the data** — only the Secret changed. It often follows a chart upgrade or a
Secret being deleted and recreated.

```bash
kubectl get secret <app>-credentials -n <ns> -o jsonpath='{.metadata.creationTimestamp}'
kubectl get pvc -n <ns>          # the datastore volume long predates the new Secret
```

If the Secret's `creationTimestamp` is far newer than the PVC holding the data, drift
is the likely cause. The fix is **not** to keep regenerating: either reset the
credential *inside* the datastore to match the current Secret, or restore the
original Secret value the volume was initialized with — then pin it (a fixed
`existingSecret`/`--set` value, or `helm`'s "keep existing" pattern) so future
upgrades stop regenerating it. Reconciling Secret and datastore is the goal; picking
which side is authoritative is the decision.
